Serverless Snapshot Prefetching: From First Principles to the Frontier

Aalhad Sawane, Oct 2026

What is serverless?

Function as a Service: The dominant serverless computing paradigm makes users upload their code as a stateless function. The FaaS provider (ex AWS Lambda, Azure Functions) provisions an isolated execution environment for each function and scales these environments with demand.

Each such execution environment can handle multiple invocations of its function, but atmost one at any given time.

(This serial execution of invocations in its execution environment is the default in most FaaS offerings like AWS Lambda, although other offerings exist: Google Cloud Run offers concurrency of requests on the same execution environment. This blog assumes serial execution throughout.)

One of the leading challenges that must be tackled in serverless computing:

Cold start: The latency incurred when a function invocation requires a new execution environment to be created and initialized before execution.

Different levels of isolation for the sandbox: process based, container based and VM based.
Each level has different ways to tackle cold starts:

  1. Process based: forking zygotes and CoW
  2. Container based: lazy loading layers and distroless images
  3. VM based: Snapshot restore

Industry uses VM-based isolation. Key components of this system:

  1. KVM: The Linux kernel’s hypervisor component that runs guest vCPUs, handles EPT memory translation, and manages guest execution
  2. VMM: Virtual Machine Monitor: The userspace component that manages a VM, allocates and mmaps its RAM, runs one host thread to execute a vCPU, and emulates its devices.
  3. virtio: a standard for paravirtual devices that accelerates communication between the guest device and hypervisor. The guest driver and host device exchange buffers through virtqueues in shared memory and notify each other through a transport (PCIe emulation or MMIO).

Note: Firecracker and other leading VMMs ditch PCIe entirely. Why? PCIe introduces complexity through device enumeration across multiple buses and dynamically allocated Base Address Registers (BARs), which define device memory and I/O regions. Managing this topology increases the complexity of the VMM’s device state.

  1. EPT: Extended page table, maps guest physical to host physical.
  2. VM exit / VM entry: the CPU switching from the guest into KVM (exit) and back (entry).
  3. ioctl: A standard system call to send control commands and configuration parameters to kernel drivers through a file descriptor.
  4. virtqueue: a ring buffer in guest RAM that both the guest driver and the VMM read and write. The guest places requests on it, the VMM completes them and places replies back.

  1. EPT fault: the CPU exception raised when the guest accesses a guest physical address that the EPT (extended page tables) cannot translate. It causes a VM exit into KVM. There are two common causes:

    1. Unmapped RAM page: the page has no EPT entry yet. KVM maps it and resumes the guest.
    2. Device register (e.g. virtio’s QueueNotify): the address has no RAM behind it, so every access faults. Virtio uses this deliberately as a doorbell. The guest first queues many requests in the virtqueue using plain memory writes, which cause no exit. It then writes once to QueueNotify, which causes one EPT fault and tells the VMM to process the whole batch.

Booting up

Throwback to OS 101, traditional boot up process:

Why the traditional boot exists

  • Discover unknown hardware (POST)
  • Find the OS on disk (bootloader)
  • Decompress and load the kernel

Why a microVM doesn’t need it

  • Hardware is emulated by the VMM
  • The device list is known upfront, so there is nothing to discover
  • The VMM writes the kernel straight into guest memory, so there is nothing to find

Skipped entirely

  • BIOS / UEFI
  • POST
  • Bootloader
  • Kernel decompression

This booting of microVMs directly from kernel image and root FS is called Direct Kernel Boot which is sub-second compared to traditional multisecond boots.

microVM Direct Kernel Boot

Before the guest runs (VMM)

  • Load uncompressed kernel (vmlinux) into guest memory
  • Pass device MMIO addresses to the kernel
  • Set vCPU registers to the kernel entry point
  • Start the vCPU

After the guest runs

  • When KVM detects an EPT fault in an MMIO zone, it checks if the address matches a ioeventfd region. If yes, KVM signals the associated eventfd. (VMM's io thread is alerted)

Kernel init

  • Probes only the devices it was told about
  • Mounts the root filesystem
  • Starts PID 1

Userspace init

  • Runs as PID 1
  • Starts services and the application

Restore is different

  • A snapshot restore skips kernel init, so the guest resumes with kernel and userspace already running

A step further: why stop at kernel image?

Snapshot Restore: Can we take a snapshot after kernel and userspace is initialised and running already?

This way we can skip past the delay caused by kernel init and userspace init.

What a snapshot holds

  • Taken after kernel init, userspace init, and runtime warm-up
  • Two artifacts:
    • State file: vCPU registers, device state (small)
    • Memory file: full guest RAM (large)
  • Restore resumes the guest at the exact instruction it stopped at.
  • The VMM mmaps the memory file privately instead of copying it
  • The guest runs immediately with nothing loaded (thus, no cold boot)
  • Page not resident → fault → access from file (demand paging*)
  • Fault path:
    1. Guest first touches a page
    2. EPT violation → KVM — a heavy VM-exit occurs
    3. Host page fault on the mapped file
    4. File read
    5. Guest resumes

Cold boot solved but latency added, can we fix this? (hint: Prefetching?)

*demand paging with MAP_PRIVATE: reads use file-backed pages but writes trigger CoW, creating a new private anonymous page with contents initialized with the file-backed page's contents. The snapshot file remains unaltered.

The new bottleneck

  • One invocation touches only a subset of pages (the working set)

    • Remember that one microVM can handle multiple invocations of a function. (although atmost one at any given time)

  • Each miss means one fault, one VM exit and one small read
  • Faults are many and scattered, so sequential readahead (prefetching based on spatial locality) helps only a little
  • Fix: know the working set and prefetch it before the guest asks

Where do snapshots live?

Snapshot restore so far assumed the memory file is sitting on the host. Scale that to serverless:

  • A provider hosts thousands of functions, each with its own snapshot (regenerated on new versions)
  • Each memory file is as large as the guest's RAM
  • A worker node cannot hold them all, so snapshots live in remote, shared storage like S3 for Lambda; workers keep at most a cache on local disk.

Demand paging on remote file?

mmap maps a file into the address space, and the kernel's fault path reads pages from that file. A snapshot sitting in remote storage is not such a file.

Two ways out:

  1. Handle the page fault ourselves, in userspace → userfaultfd
  2. Get the snapshot onto the host as a file, and let the kernel and its page cache do the work → mmap + mincore

userfaultfd

The userfaultfd syscall in Linux lets a user-space program handle virtual memory page faults on its own instead of relying solely on the kernel.

for our problem this reduces to: mmap for pages that are not in a file on disk.

  • Added to Linux in 2015 (v4.3)
  • Built for postcopy live migration: resume the VM on the new host first, pull its pages over the network as it touches them. Same problem as ours.
  • Register a memory region → faults on it go to a userspace handler uffdh, not the kernel's file-backed path
  • Thus, the custom userspace handler can fetch the page from anywhere: local disk, remote store, another machine
  • uffdh is a seperate process (not part of the VMM)

Overhead: uffdh only manages the contents of a page, the actual page allocation and copying of the contents is still made by kernel.

This means using userfaultfd leads to heavy context switching. (first from kernelspace to userspace for fault handling then userspace to kernelspace for actual allocation)

Fault path

  1. Guest first touches a page.
  2. EPT violation → KVM → host page fault.
  3. The kernel detects the userfaultfd-registered region and notifies the userspace handler uffdh.
  4. The handler fetches the page contents from snapshot storage.
  5. uffdh calls ioctl(UFFDIO_COPY) which transitions to kernelspace where kernel copies the contents, and updates the page tables.
  6. Guest resumes.

Still demand paging: one fault per page. So we prefetch.

Host Page Cache

  • The page cache holds file-backed pages (plus swap-cache pages for anonymous memory being swapped)
  • Anonymous memory is not in the page cache
  • A snapshot’s memory file is a regular file, so even with userfaultfd its contents are treated as file-backed pages. Thus it's pages would go in host page cache in a naive setup. Serverless has different requirements.

Prefetching with userfaultfd (REAP, Faast) in 2 phases

Record phase (first invocation)

  • uffdh serves every fault, so it sees every page the invocation touches
  • It writes those pages' contents into a compact working set file

Invocation phase (later restores)

  • The handler reads the working set file in one go and installs all its pages before the guest asks
  • It reads with direct IO, skipping the page cache: the data ends up in private anonymous memory anyway, so caching it would only double-buffer
  • Pages outside the working set still fault lazily

Why direct I/O? Serverless involves countless ephemeral functions, using page cache for all snapshots would pollute cache and lead to heavy thrashing

Disadvantages

  • A second copy of the working set, stored per function
  • Every snapshot page is copied through uffdh's userspace buffer into guest RAM.
  • Anonymous memory is private to each VM: 10 VMs of one function = 10 copies. No sharing.
  • Remember that since we are using O_DIRECT, we bypass the host page cache, preventing cached snapshot pages from being reused across VMs.

gap: I could not find a quantitative study evaluating the tradeoff of time saved by sharing vs time lost in page cache thrashing if we were to use O_DIRECT when choosing to use or not use O_DIRECT in serverless workloads

What is mincore?

mincore: syscall answering which pages of this mapping are in RAM right now?

  • Input: a range of the process's virtual memory
  • Output: a byte array, one byte per page; lowest bit set = resident
  • For a file mapping, resident = in the page cache

It is a snapshot taken after the fact:

  • No ordering: it says nothing about when a page arrived
    • Can't distinguish recency of pages
  • No cause: a page could be there because the guest touched it, or because the kernel's readahead pulled it in
    • Can't distinguish demand from readahead prefetch

mmap + mincore (FaaSnap)

Idea: don't intercept faults. The kernel's page cache already loads snapshot pages on demand, so use it to record and to prefetch.

Record: ask the page cache what got loaded

  • mmap the snapshot and run one invocation
  • Every page the guest touched got faulted into the page cache
  • Call mincore over the mapping: the cached pages are the working set
  • Copy them, back to back, into one working set file

Why copy at all? In the snapshot, these pages are scattered across gigabytes, so reading them means many small random reads. Packed into one file, they take a few large sequential reads.

Prefetch: get the working set into RAM early

Goal: by the time the guest touches a working-set page, that page is already in RAM.

Plan: a background thread reads the whole WS file. It ignores the data; reading is just a way to pull the file's pages into the page cache.

How the page cache finds a page

  • Each cached page is labelled by the file it came from and its position in that file
  • Each page of guest memory is backed by one file, at one position in it
  • When the guest first touches a page, the kernel asks the page cache: "do you have this file, at this position?"
    • Yes → use that copy, no disk read
    • No → read it from disk

The mismatch

  • The background thread's read caches the working set under the WS file's label
  • Guest memory is mapped from the snapshot, so a guest fault searches under the snapshot's label
  • The search misses and goes to disk, even though the exact bytes are already sitting in RAM, just under a different name (as an offset in WS file instead of snapshot file)

Fix: back those pages with the WS file

  • mmap the WS file over the snapshot mapping, so each working-set page of guest memory is backed by its copy in the WS file
  • Now a guest fault searches under the WS file's label → found → no disk read
  • Every other page is still backed by the snapshot

Bonus: the page cache belongs to the whole host, not to one process

  • Every sandbox of the same function searches for the same labels and finds them
  • So there is one copy of the working set in RAM, however many sandboxes run

But mmap is for contiguous ranges?

  • In the snapshot, working-set pages are scattered. In the working set file, they are packed.
  • One mmap maps one contiguous range to one contiguous range
  • So every contiguous range of working-set pages needs its own mmap → thousands of them (since contiguous ranges are rare, as most WS is scattered).
    • each arrow in the following diagram represents 1 mmap
  • FaaSnap's fix is to merge contiguous ranges separated by small gaps
  • But then the gap pages get copied into the file and read on every restore, even though no invocation touched them
  • So the trade-off is fewer mmaps vs. a bigger file and wasted IO

Where both fall short

  • Two copies on disk: the snapshot, plus a working set file that copies some of its pages
  • Recording in userspace: uffdh sees faults one at a time, and mincore only sees the end result

Better: record just which pages of the snapshot were loaded, as a list of page numbers. On restore, load exactly those pages from the snapshot file itself into the page cache.

No second file, no mmap juggling, and the page cache is still shared.

That needs a hook inside the kernel, at the point where pages enter the page cache. (hint: eBPF)

What is eBPF?

extended Berkeley Packet Filter

eBPF: small sandboxed programs you load into a running kernel, safely.

  • Verifier: checks every program before it runs
    • Every loop must end
    • No memory access outside what it is given
    • Only approved kernel functions may be called
    • If any check fails, the kernel rejects the program
  • Hook: the program is attached to an event and runs every time that event happens
  • Map: a key-value store that lives in the kernel, readable and writable by both the eBPF program and userspace

SnapBPF: a novel solution that utilises eBPF for prefetching serverless snapshots

The hook SnapBPF uses: kprobe

kprobe: a hook on (almost) any kernel function.

  • Whenever that function runs, the attached eBPF program runs first
  • The program receives the function's arguments

SnapBPF hooks add_to_page_cache_lru, the function called every time a page enters the page cache.

Its arguments say:

  • which file the page belongs to
  • which page of that file it is (its offset)

This is exactly the point that the end of the previous section asked for.

SnapBPF: record phase

  1. VMM restores a sandbox with the snapshot mmaped, the same as plain demand paging
  2. Before the guest runs, VMM attaches the capture program to the kprobe
  3. Function is invoked. Each guest miss brings a page into the page cache, and the program fires
  4. Program keeps only pages of the snapshot file, since every file on the machine passes through this hook
  5. It stores each page's offset in an eBPF map
  6. After the invocation, the VMM reads the map and saves the offsets to disk

Readahead is turned off during recording. Otherwise the kernel would also pull in neighbouring pages the guest never touched, and they would be recorded as working set.

What gets saved: a list of page numbers, a few KB in size, not copies of pages. There is no second copy of the working set.

SnapBPF: invocation phase

Before any restore, the VMM prepares the saved offsets:

  • Group consecutive pages into ranges, e.g. pages 8 to 11 become one range
  • Sort the ranges by when they were first touched during recording, so the earliest-needed pages are read first

  1. New sandbox restores, and the VMM loads the ranges into an eBPF map
  2. VMM attaches the prefetch program to the same kprobe
  3. VMM touches the first page of the snapshot, which triggers the hook
  4. The program walks the ranges in order and asks the kernel to read each one from the snapshot file into the page cache
  5. After the last range, the program detaches itself

Pages are cached as (snapshot, pg N), which is exactly what the guest looks up. They are hits, with no remapping.

One problem: eBPF cannot do IO

The verifier forbids an eBPF program from issuing disk reads or modifying the page cache.

  • Fix: a kfunc, a kernel function that is explicitly made callable from eBPF
  • SnapBPF adds one kfunc, snapbpf_prefetch
  • It wraps the kernel's own readahead routine, the same code Linux uses to prefetch file pages

So the eBPF program decides what to read, and existing, trusted kernel code does the reading.

Wait: aren't these scattered reads?

FaaSnap built a packed file to get sequential reads. SnapBPF reads directly from the snapshot, where working-set pages are spread out.

  • On spinning disks, this would be slow because each jump means a disk seek
  • Modern SSDs handle many small, non-sequential reads well
  • Grouping pages into ranges still reduces the number of requests

Side by side

userfaultfd (REAP, Faast) mincore + mmap (FaaSnap) eBPF (SnapBPF)
Records in userspace userspace kernel
Saved to disk page copies page copies (+ gaps) page numbers only
Memory across sandboxes one copy each shared shared
Extra mmaps none many none

The other waste: fresh allocations

Prefetching decides which snapshot pages to load early. There is a second question: should some pages not be loaded from the snapshot at all?

Two page tables, two owners

A guest memory access is translated twice:

  • Guest page table (owned by the guest kernel): virtual address → guest page number, e.g. pg 500
  • EPT (owned by KVM): guest page number → real RAM on the host

After a restore, guest page N is backed by page N of the snapshot file. The first time the guest touches pg 500, the EPT has no entry for it, so KVM steps in and reads page 500 from the snapshot.

The key limit: KVM sees only the page number. It never sees why the guest touched it. (it could have been a fresh allocation malloc() call)

Why this wastes reads

The guest touches a page for one of two reasons:

  1. Reading data it already has, e.g. model weights loaded before the snapshot → needs the snapshot's contents
  2. Allocating new memory, e.g. a fresh buffer for this request
    • The guest's allocator hands out a page it considers free
    • That page's old contents in the snapshot are leftover garbage
    • The guest will zero or overwrite it immediately

Both reach KVM as the same fault on a page number, so both get a disk read. For case 2, that read is pure waste on the critical path.

It also confuses the recording:

  • New allocations can land on different free pages in each invocation
  • So the recorded working set includes pages the next invocation won't use, and misses ones it will

What KVM should do for case 2: hand the guest a zeroed page from host RAM, with no disk read. The hard part is knowing it is case 2.

Why a zeroed page?

For a fresh allocation the guest doesn't care what the page contains, since it will overwrite it. So why not hand over any spare page?

  • Safety: a spare host page may still hold another VM's or process's data, so handing it over unwiped would leak it. Linux therefore always zeroes a page before giving it out.
  • Cost: zeroing happens in RAM, which is far cheaper than a disk read
  • Correctness: the guest expects garbage in a newly allocated page, so zeros are as good as anything

So "zeroed page" really just means a new page from host RAM instead of from the snapshot.

Prior work: find the free pages before restoring

Both need the same answer: which pages of this snapshot are free memory? Those pages can then be served as zeroed pages instead of read from disk.

FaaSnap: make free pages recognisable

  • A freed page normally keeps its old data, so in the snapshot it looks exactly like a page in use
  • Fix: patch the guest kernel to write zeros into every page it frees
  • Now every free page in the snapshot is all zeros
  • Scan the snapshot. Any all-zero page is served as a zeroed page, with no disk read.
  • Even if an all-zero page was in use, serving zeros is still correct, because its content was zero anyway

Faast: read the guest's free list

  • The guest kernel keeps its own record of which pages are free
  • That record lives in guest memory, so it is inside the snapshot
  • Read it out of the snapshot file to get the list of free pages

Costs of both

  • A pass over the whole snapshot (as large as guest RAM), repeated for every new snapshot
  • Both only know what was free when the snapshot was taken
    • The guest frees and reallocates memory while it runs, and they cannot see that

SnapBPF: let the guest tell KVM, at allocation time

Paravirtualization (PV): modify the guest kernel so it knows it runs in a VM and cooperates with the host.

The problem is the channel

  • An explicit call to the host on every allocation means one VM exit per allocation, which is far too expensive
  • But a fault reaches KVM anyway on first touch, and the only thing it carries is the page number
  • So encode the hint in the page number itself

PV PTE marking

  • The guest kernel allocates pg 500 for new data
  • In its page table, instead of pg 500 it writes pg 500 with the top bit set
    • That number is far beyond the guest's real RAM, so no real page has it
    • It is a "mirror" of pg 500
  • The guest touches it → no EPT entry → fault reaches KVM, the same exit that would have happened anyway
  • KVM checks the top bit:
    • Set → fresh allocation → back it with a zeroed page from host RAM, no disk read
    • Clear → normal fault → read from the snapshot (served from the page cache if prefetched)
  • KVM maps that zeroed page at both the mirror and the real pg 500. Later accesses through either number reach the same memory.

Net effect

  • No scan, no preprocessing
  • No extra VM exits
  • Works for allocations made after the snapshot, which scanning can never see

SnapBPF results

One sandbox

  • Faster than REAP: no page copies through userspace
  • Matches or beats FaaSnap: no copy into a working set file, and no gap pages

10 concurrent sandboxes of one function

  • Up to 8× lower latency than REAP (BERT): the working set is read once and shared
  • Up to 6× less memory (BFS, BERT): REAP keeps one copy per sandbox

Which part helps which function

  • Allocation-heavy functions (image processing) gain most from PTE marking: over 2× faster
  • Functions with a large loaded model (RNN, BERT) gain almost entirely from prefetching

Open questions

  • Same input every time: all 10 sandboxes ran the same input, which is the best case for sharing. Varying inputs is left to future work. This heavily favours the strong results for snapBPF.
  • Kernel changes in three places: a new kfunc on the host, a KVM patch, and a modified guest kernel, which is a real cost to deploy.
  • Where is the snapshot coming from: the snapshot must be a file on the host so the page cache can hold it. That brings back our opening question about where snapshots live. AWS has a really complicated way of answering that question which leads to a bunch of other scheduling and placement decisions it makes not just at local node level but at AZ level, whether snapshots are in S3, the AZ distributed cache or local disk. This state is not captured in any of the approaches considered.

Closing thoughts

Serverless computing still has lots of room for optimisations that can be made and SnapBPF was a refreshing reminder of the same.

There is much more juice that can be squeezed out.

The rise of AI agents is accelerating demand for serverless computing, as autonomous workloads require scalable, on-demand compute to execute tasks in isolated environments. Exciting years ahead in serverless.
