LLM inference comes to serverless? Decoding ServerlessLLM

Aalhad Sawane, Oct 26'

Based on ServerlessLLM and its OSDI ’24 paper.

Why LLM inference on serverless is growing in popularity?

  • A dedicated GPU per model sits idle between requests. GPUs are expensive.
  • Serverless runs a model only while requests arrive, and bills per request.
  • Many models share the same GPUs.
  • Thus, cost effective especially for sparse and spiky workload patterns.

What happens when a request arrives for a model that isn't on any GPU?

*refer to the start of this article if unfamiliar with serverless.

Waiting for the model to start

  • The request waits while the model is started.
  • Cold start: the startup wait a request pays when no running instance of its model exists.
  • To limit it, providers keep an instance running for a while after its last request (keep-alive).
  • Azure production trace, 5-minute keep-alive:
    • Over 40% of functions cold start on more than 25% of invocations.
    • About 25% cold start on more than 60%.
  • (Trace of general serverless functions, not LLM inference.)

How does ServerlessLLM aim to minimise cold starts and make the GPU placement and request scheduling serverless-friendly?

Why do cold starts hurt LLM inference?

Time to First Token (TTFT): time between sending a prompt and receiving the first generated token.

  • Apps stream tokens, so the user sees nothing until TTFT.
  • A warm request goes straight to computing.
  • A cold request has steps before that.

What are those steps?

The path of a cold request (for serverless LLM inference)

Step wise latency

  • Download: LLaMA-2-70B is 130GB. Over a fast 5GB/s network, at least 26s.
  • Load: even with weights already on local NVMe SSD:
    • OPT-30B onto 4 GPUs takes 34s.
    • LLaMA-2-70B onto 8 GPUs takes 84s.
  • Compute: generating a token takes under 100ms.
  • Moving bytes dominates. Providers report tens of seconds.

How do we avoid moving those bytes at request time?

The obvious fixes

Keep GPUs pre-loaded

  • Hold GPUs loaded with the model ahead of demand (oversubscribing).
  • Reserved GPUs sit underutilised.
  • Works for small models like ResNet and BERT.
  • One LLM needs several costly GPUs. Idle reserved GPUs are what serverless was meant to avoid in the first place.

What if the weights are cached closer to the GPUs instead?

Cache weights closer to the GPUs

  • Server DRAM: skips the download.
    • LLM weights are huge: Grok-1 is over 600GB, Mixtral-8x22B about 280GB.
    • DRAM holds only a few. Each miss brings the download back.
  • Storage servers on a fast network: the download is local.
    • Still over 20s even with a 100 Gbps NIC.
    • A 210GB-memory cache instance costs $16.3/h, the price of an 8-GPU server.

All three buy extra hardware or waste GPUs. Is there capacity GPU servers already have, unused?

Exploiting the GPU server's storage heirarchy

  • Besides GPUs, a server has host DRAM and SSDs.
  • An 8-GPU server can hold up to 4TB of DRAM and 64TB of NVMe SSD.
  • Serverless inference leaves most of it unused.
  • Weights would move through these tiers: remote storage, SSD, DRAM, GPU.

How fast can bytes move between them?

Each hop toward the GPU is faster than the one before.

So what if the weights just live on the server?

Keep the weights on the server

  • Store weights on the GPU server's SSD. Keep recently used ones in DRAM.
  • No download at request time. No new hardware.
  • Capacity and bandwidth grow with every server added.

Does that fix the load time?

Local SSD isn't enough yet

  • LLaMA-2-70B is 130GB. A local NVMe SSD reads about 12GB/s, so the disk alone needs about 11s.
  • PyTorch loading from that same SSD takes 84s.
  • The disk isn't the bottleneck. How the weights are stored and read is.
  • That format was built for training: written often, loaded rarely.
  • Serving is the opposite: written once, loaded on every cold start.

What exactly is stored in that file?

What is a checkpoint?

The obvious guess: a memory snapshot

Memory snapshot: a copy of a program's memory written to disk, so it can be read back later.

  • Natural guess: the saved model is one, read back in a single sequential read.
  • But a snapshot copies everything in memory. Most of it is unnecessary.

What is necessary to save?

Save only what can't be rebuilt

  • Only the weights can't be rebuilt. They come from training. Plus model architecture.
  • Checkpoint: the saved weights plus a description of the model, enough to rebuild it.
  • Also a raw memory snapshot would be tied to the GPU memory addresses of the run that made it, and would fail on a different GPU.

What does that description contain?

The LLM checkpoint

Tensor: a named multi-dimensional array of numbers. A model's weights are many tensors.

  1. Model execution files: the architecture, each tensor's shape and size, and a plan for which GPU gets which tensor.
  2. Parameter files: the tensors' raw binary data, in any order.
  • Almost all the bytes are in the parameter files.

Same weights. The checkpoint drops what can be rebuilt.

So what does loading a checkpoint onto GPUs actually involve?

Why loading a checkpoint is slow

What loading does

  1. Build the model from the execution files.
  2. Allocate memory on each GPU.
  3. Read the tensors from storage, one by one.
  4. Copy each tensor into GPU memory.
  • The steps run in this order, one at a time. Steps 3 and 4 repeat for every tensor.

Why is loading built like this?

Built for training, not serverless

  • Checkpoint tools (PyTorch, TensorFlow, ONNX) were designed for training and debugging.
  • There, a checkpoint is persisted often and loaded rarely. Nobody optimised the read path.
  • Serverless inference is the opposite: persisted once, loaded on every cold start.

What this mismatch costs?

  • Tensors are read one at a time. A third of them are under 1MB, so the SSD gets many small reads and sits underused.
  • Building the model and loading the bytes can't overlap. The GPU waits for each step.

A checkpoint built for quick loading (proposed by ServerlessLLM)

Key: Encourage big sequential reads

  • Store each GPU's tensor bytes contiguously in one file: a partition.
  • Partitions hold raw bytes only. No shapes or names inside, so the loader can read them in large chunks.
  • One partition per GPU: each GPU's bytes form a single sequential stream.

With only raw bytes, how do we find a particular tensor?

The tensor index

  • Tensor index: a small file saying where each tensor's bytes sit in its partition.
Tensor GPU Offset Size
layer.weight 0 0 32 MB
layer.bias 0 32 MB 8 KB
  • The model manager, a loader process, allocates GPU memory and copies each partition there as-is. So a tensor's address is the partition's start address (its base address) plus its offset.
  • No parameter bytes are needed to work this out.

Does building the model need the parameter values?

Building the model without the values

  • A tensor in the model has an address, a shape and a type. None of these is a parameter value.
Tensor field Comes from
Shape, type Execution files (the model definition)
Address Base address (model manager) + offset (tensor index)
  • So the model can be built before its values arrive. It just can't run until they do.
  • Ordinary construction allocates and fills its own tensors. Here, each tensor is pointed at memory the loader has already allocated.

Can we build the model while the bytes are still loading?

Two processes, two jobs. Inference starts once both finish.

Which piece supplies what to the model?

Shape and type: execution files. Offsets: tensor index. Base addresses: model manager.

Data path for the loader (model manager)

  • Two kinds of interconnect: the SSD link, and a dedicated PCIe link for each GPU.

From SSD to GPU: the options

  • Normal buffered read: SSD → OS page cache → program buffer → GPU. The SSD transfers data into the page cache using DMA; the kernel then copies it into the program buffer, consuming extra memory bandwidth. Large checkpoint reads can evict useful cached pages (cache thrashing).
  • mmap: Maps the file into virtual memory. On first access to a nonresident page, a page fault triggers demand paging from the page cache. Performance depends on cache state and page-fault overhead. (Safetensors: about 112K page faults on LLaMA-2-7B.)
  • Direct I/O: SSD → program buffer → GPU. The SSD transfers data into the program buffer using DMA, bypassing the page cache. If the buffer uses pageable memory, the GPU driver typically copies data into a pinned staging buffer (host memory locked against paging) before transferring it to the GPU.
  • Direct I/O into pinned memory: SSD → pinned host buffer → GPU. The SSD writes directly into the pinned buffer using DMA, bypassing the page cache; the GPU then transfers data using DMA, avoiding an intermediate CPU-mediated copy.
    • This is what ServerlessLLM does.

ServerlessLLM's data path

  • GPU DMA: the GPU's copy engine pulls the bytes from pinned DRAM over PCIe by itself. The CPU only issues commands. DMA controllers do the job.
  • Chunk: a fixed-size slice of a partition (16 MB). The pinned pool holds chunk-sized buffers.

Pipelined SSD-to-GPU data path

  • An SSD has many internal channels, so several I/O threads read different chunks at once.
  • Each GPU has its own PCIe link, so partitions for different GPUs copy in parallel.
  • Pipeline: while one chunk copies to the GPU, the next is read from the SSD.

Gain from each optimisation

Start from reading tensor by tensor on RAID-0 NVMe, then add one optimisation at a time. Each figure is the gain over the previous one:

  • Bulk reading: fixed 16 MB chunks instead of one read per tensor (tensors range from a few KB to hundreds of MB, and a third are under 1 MB): 1.2x.
  • Direct I/O: 2.1x.
  • Multiple threads: 2.3x.
  • Pinned memory: 1.4x.
  • Pipeline: 1.5x.

Checkpoint Loader perf comparison

LLaMA-2-70B from local NVMe (12 GB/s):

  • PyTorch: 84s. Safetensors: about 48s. ServerlessLLM: about 10s, close to the SSD's limit.
  • It saturates each storage device it reads from, so load time depends only on checkpoint size and the bandwidth of the tier it sits in.
  • Different servers hold a model in different tiers, so the same model loads at different speeds on different servers.

So which server should a request go to?

Which server should run a request?

Key: Every server holds different models in different tiers

Naive availability-driven (ignores locality)

  • Availability-driven: pick any server with a free GPU. Here, Server 1.
  • It ignores where B is stored, so B loads from SSD: slow.

What if we pick the server where B is already close to the GPU?

Locality-driven with wait

  • Locality-driven: pick the server that stores the model in the fastest tier. Here, Server 2.
  • Its GPU is busy, so B waits until A finishes. Nobody knows how long that takes, and Server 1 sits idle.

Locality-driven with preemption

  • Stop A and run B on Server 2 straight from DRAM. Restart A on Server 1: reload it, then recompute its progress.
  • B starts fast, but A's token stream stalls: its TPOT spikes. (Can we get rid of A's stalling?)

Locality-driven with Live Migration

Key: A keeps generating while it moves

  • Load A on Server 1 while A keeps running on Server 2. A's checkpoint already sits in Server 1's DRAM, so this load is fast.
  • Locality influences scheduler's choice of migration destination choice; explained in following parts of the post.
  • Hand A's progress to Server 1. Server 2's GPU is now free for B.

What exactly is A's progress?

A request's progress

  • KV cache: intermediate results (attention keys and values) the model keeps for every token so far, so it doesn't redo work for earlier tokens at each step.
  • A request's progress is its tokens (the prompt plus the output so far) and the KV cache built from them.
  • The KV cache can always be rebuilt from the tokens.

Which of the two should move?

Move tokens, not the cache

Option What moves Cost
Snapshot the process Everything Tens of seconds to minutes
Move the KV cache 1–10s of GB Floods the network
Move the tokens 10–100s of KB Destination rebuilds the KV cache
  • Per token: about 0.5 MB of KV cache against 4 bytes for the token id (7B-class model).

Rebuilding the cache takes time. How much?

Why rebuilding is cheap

  • Decode: generating output. Each token depends on the previous one, so tokens come one at a time, and every step reads all the weights from GPU memory.
  • Prefill: processing tokens that are already known. All of them go through the model in one pass.
  • Rebuilding a KV cache is a prefill: about 10x faster per token than decoding. (Paper: rebuilding 1000 tokens takes about as long as generating 100.)

Meanwhile the source keeps generating. Can the destination catch up?

Multi-round syncing b/w src and dest

  • Round 1: the destination rebuilds the KV cache for all tokens so far. Meanwhile, the source generates new tokens.
  • Each next round: the destination only has to rebuild the tokens generated during the previous round. About 10x fewer each time, since prefill is about 10x faster than decode.
  • When the gap is small, the source pauses, sends the last few tokens, and the request router redirects the request to the destination.

Catch-up works only because prefill is faster than decode. If it were slower, the gap would grow.

In the last round, where the source is paused for a while before it starts on destination, as the gap is small and tokens are very few, the effect of migration on latency is negligible.

Two operations: load and migrate

  • Load: copy a model's checkpoint to a GPU. Its latency depends on which tier holds the checkpoint, and on the loads already queued.
  • Migrate: move a running request to another server without stopping it. The destination loads the model, then rebuilds the KV cache.
  • A waiting request pays the latency of whichever operations it needs. The scheduler has to know both before it acts.

Estimating each operation

Estimate Formula
Load a model queue wait + model size ÷ bandwidth of the slowest tier
Migrate a request per-token rebuild cost × tokens so far + fixed cost
  • A live migration also includes loading the model on its destination. That part is a load, estimated by the first row.
  • Estimate tokens generated so far as elapsed generation time ÷ average time per token, avoiding the need to track token counts explicitly.

Keeping the estimates accurate

  • Loading is pipelined, so the slowest tier sets the pace.
  • Loads that share a path (remote → SSD, SSD → DRAM) run one at a time per server, so each gets the full bandwidth. Each GPU has its own PCIe link.
  • Load time depends only on checkpoint size and bandwidth, so it is predictable. mmap-style loading wasn't.
  • Servers report measured loading times, which refine the estimates.

How can the scheduler use these estimates?

Choosing a server

Key: Estimate every server's startup time, then pick the lowest

  • Startup-time-optimised scheduling: schedule the model onto the server that minimises its startup time, given where each server holds its checkpoint.
  • In the example: Server 1 loads B from SSD. Server 2 first migrates A to Server 1 (how is A's destination selected? explained below), then loads B from DRAM. (as migration does not impact latency of A non-trivially)

Moving A may displace another model. Where does that stop?

Choosing A's destination

  • Moving A can displace another model, which displaces another. Searching every chain is messy.
  • The serverlessLLM scheduler avoids it: A may only go to a server that already has a free GPU. No chains. (This misses some optimal paths in certain scenarios though, e.g. A's fastest server has no free GPU, thus there is a room for improvement in this scheduling algorithm)
  • Among those servers, A goes where it loads fastest: queue wait + size ÷ bandwidth of the tier holding A there. (In the example, Server 1, where A sits in DRAM.)
  • If B needs more GPUs than are free, several running models must move. A knapsack-style dynamic program picks which ones, minimising total migration time.

The scheduling procedure

  • For each server, the estimate is B's load time there, plus the cheapest migrations if GPUs are short. The lowest wins.
  • Requests are handled one at a time. If no server can free enough GPUs, the request waits and is retried.

The three contributions of ServerlessLLM

Does it pay off?

Key: Compare against systems that load models the usual way

  • Ray Serve (extended for serverless), Ray Serve with Cache (adds a local SSD cache), and KServe. Four servers, four A40 GPUs each, bursty trace-shaped requests.

GSM8K, average model startup:

Model Ray Serve Ray Serve with Cache ServerlessLLM
OPT-6.7B 12.1 s 8.2 s 0.8 s
OPT-30B 213 s 199.2 s 7.5 s
  • A 100 Gbps network cuts Ray Serve's OPT-6.7B startup to 3.8 s. Still 4.7x slower.

Where the gain comes from

  • Loader: cold starts drop below a second.
  • Scheduler and migration: latency stays flat as load rises. A baseline with only a cache slows down once GPUs run short.
  • Limit: neither creates GPUs. Once every GPU is busy, latency rises.

Where the design is thin

Key: The scheduler is greedy. Each request is optimised alone.

  • Each request goes to the server with the lowest estimated startup at that moment.
  • Dynamic programming picks the destination of one migration only based on free GPUs at the current time. It does not have an estimate on when a job ends in future which could be used to make better decisions.
  • The paper compares against random scheduling and Shepherd*, which uses the same estimator and picks the same server.
  • Issue: never compared with a non-greedy scheduler or an offline optimum.

Can the cheapest choice now be the wrong choice overall?

Greedy is not perfectly optimal: Two requests, one good slot

  • X costs 2 s on Server 1 and 3 s on Server 2. Y costs 2 s on Server 1 (DRAM) and 9 s on Server 2 (SSD only).
  • X goes first, takes Server 1 for a one-second gain, and reserves its GPU. Y is left with Server 2.

Does the search miss better plans even for one request?

Possible migration chains are never searched

  • B wants Server 2, where A runs. The only free GPU is on Server 3, where A loads from SSD. Server 1 holds A in DRAM, but its GPU is busy with C.
  • Moving C to Server 3 and A to Server 1 would start B sooner. The scheduler never considers it.

What the estimate leaves out

  • Output length: nobody knows how long a request will keep generating. A victim about to finish would free its GPU for nothing, yet the scheduler migrates it, since waiting is never compared. A long-running victim is costly to move, since rebuild cost grows with tokens so far.
  • DRAM contents: placing B queues it into the server's DRAM pool and evicts the models loaded longest ago. A near-tie (8.0 s against 8.3 s) can evict what the next request needs.
  • GPUs: a migration takes a free GPU on its destination. The next request may find none.
  • Disruption: only B's startup is minimised. A's pause costs nothing in the estimate.

Other scheduler problems

  • Static estimates: nothing is learned at runtime. Bandwidths come from a start-up benchmark, and the rebuild constants from config.
  • Polling: one control loop wakes once a second, so a cold start can wait up to a second before it is considered.
  • Remote storage is outside the scheduler: models are downloaded from the remote blob storages at deploy time, to the nodes in a placement spec (by default, one node). At scheduling time, servers without a local copy are skipped, since downloads are "difficult to estimate". So placement limits what scheduling can do.

Measuring the gap

  • No online scheduler is optimal: arrivals and output lengths are unknown.
  • Replay the same trace through an offline scheduler that knows the future, and report the gap.
  • Widen the search: allow chains, and assign pending requests together.
  • Price eviction into the estimate.
  • Expect the gap under contention, when free GPUs are scarce. With spare GPUs, any scheduler looks good.

Newer work

  • BlitzScale (OSDI '25) and λScale (arXiv) load from GPUs that already hold the model, over the GPU network, and start serving before the whole model has arrived.
  • HydraServe (NSDI '26) fetches one model across several servers and overlaps the other cold-start stages.
  • PhoenixOS (arXiv) restores whole GPU processes, loading buffers on demand. (dont write arxiv write conference)
  • Llumnix (OSDI '24) migrates by copying the KV cache while decoding continues, with a pause of about 20–30 ms.

What does the evaluation hold fixed?

What the evaluation holds fixed

  • Every instance served one request at a time. With batching, as in vLLM, an instance holds many requests. A migration must rebuild all of them, but the rebuild estimate reads one request's token count.
  • Inputs were cut to 2048 tokens. Rebuild cost grows with tokens, so long contexts are untested.
  • No public LLM serverless trace exists, so an Azure function trace was mapped onto models.

What to take away

Key: ServerlessLLM turns the storage and memory already inside GPU servers into a fast path for model startup.

  • Fast multi-tier checkpoint loading: a loading-optimized checkpoint format and a multi-tier loader use the full bandwidth of the storage hierarchy.
  • Live migration of inference: a new request can use a server's local checkpoint, while the request it displaces keeps running with minimal interruption.
  • Startup-time-optimized scheduling: estimates where each checkpoint sits on every server and picks the server that starts the model soonest.
  • Result: 10-200x lower latency than naive serverless setups and 6x speedup from SafeTensors.

Closing Thoughts

Inference is growing rapidly, and so is serverless inference.

Fundamental questions remain open, with substantial room for improvement.
