The 6 step startup process:

TLDR; per-step parameter dependence

Step Parameter Dependency
1. Framework Bootstrap Constant, regardless of model
2. Tokenizer Initialization Tokenizer size (vocabulary size)
3. Model Loading Model parameter size
4. Torch Compilation Number of layers and model complexity (compiled graph size)
5. KV Cache Profiling Model parameter size
6. CUDA Graph Capturing Model parameter size and number of batch sizes

Every step is explained with key takeaways below.

Step 1: Framework Bootstrap Step

  1. Platform Detection — Identify the execution environment (CUDA or CPU).
  2. Dependency Loading — Import PyTorch, Transformers, and required libraries.
  3. Model Metadata — Load model configuration and tokenizer metadata.
  4. Worker Setup — Initialize GPU contexts and shared-memory structures.

Famework Bootstrap takes ~10* seconds regardless of model, only depends on vLLM implementation

*This step is CPU-bound, and was tested on Intel Xeon Platinum 8568Y+

Step 2 & 3: Tokenizer and Model Loading

  • Tokenizer size directly affects latency of Tokenizer loading linearly, which is determined by vocabulary size of the tokenizer.
  • Model size, regardless of architecture, affects latency of model loading linearly.

Step 4: Torch Compilation

Problem: by default, PyTorch runs the model one operation at a time (eager execution). It is simple and easy to debug, but slow.

  • PyTorch runs operations one by one.
  • Each one means Python dispatch plus a small GPU kernel launch.
  • Many tiny kernels mean the GPU sits idle between launches.

Fix: compile the model.

  • Capture the operations as a graph.
  • Generate fewer, optimized GPU kernels from transforming the graph.

Trigger: a dummy forward pass.

  • A representative input is pushed through the model once.
  • This exposes the model's computation to the compiler.
  • It is a warm-up, not a real request.

TorchDynamo and TorchInductor

  • Capture (Dynamo Transformation): TorchDynamo intercepts Python execution and records tensor ops as an FX graph (PyTorch's intermediate representation of the model). This step is called
  • Optimize (Graph Compilation): TorchInductor takes the FX graph, fuses ops and generates optimized GPU kernels.
  • Result: a compiled model with fewer launches per forward pass.

Model architecture affects compilation time

Compilation time (both Dynamo transformation, Python to FX, and graph compilation, FX to GPU kernels) depends on:

  • Number of layers
  • Layer complexity

So compilation time follows the model's architecture, not just its parameter size.

Things to know about torch compilation in vLLM:

  • Split graph: vLLM compiles each layer in pieces and leaves attention out. Attention runs eagerly (op by op, without compilation), and everything between attention calls runs as compiled kernels.



  • One graph for all batch sizes: naive PyTorch bakes the exact input shape into the compiled kernels, because known sizes allow faster code. A different batch size, such as 8 going to 16, breaks that assumption, so it recompiles. vLLM can skip this because the sequence of operations is the same for any batch size, and only the number of tokens each one processes changes. So vLLM compiles with batch size left as a variable (which allows continuous batching) and reuses the same graph for every batch size, at the cost of slightly less specialized kernels.



  • Cost: compilation is slow once (cold-start latency), but every later forward pass is faster, which thus makes up the cost in steady-state latency for most workloads. vLLM also caches the compiled result on disk, so later startups skip most of it.

Step 5: KV Cache Profiling

Goal: find how much GPU memory can go to the KV cache (the stored attention state of past tokens, so they aren’t recomputed).

  • vLLM does a dummy run to measure the model’s memory use.
  • Whatever memory is left over becomes the KV cache.

Observations:

  • Profiling time grows linearly with model size.
  • MoE (mixture-of-experts) models deviate from this trend. (linear correlation does not hold)

Step 6: CUDA graph capturing

Goal: cut the cost of launching GPU kernels one by one.

  • vLLM does a dummy run and records all the GPU operations into a CUDA graph.
  • Later, the whole graph is replayed with a single launch.

Relation to model size: larger models take longer, because the dummy run is longer.

Relation to batch sizes: a CUDA graph is recorded for one fixed batch size, so every batch size needs its own capture.

  • With continuous batching, requests join and leave the batch dynamically, so the batch size keeps changing.

  • vLLM therefore captures graphs for a predefined set of batch sizes, for example 1, 2, 4, 8, 16, and so on.

  • At runtime, it pads the batch up to the nearest captured size. For example, 5 requests run on the graph for 8.

  • More captured sizes means a longer startup (since every size needs its own CUDA graph capture) but makes up for it in latency with more granular batching.

  • Again, we can see a cold-start latency vs steady-state latency tradeoff.

Closing Thoughts

While significant effort goes into optimizing vLLM’s steady-state performance, cold-start latency remains relatively underexplored.

With rising adoption and increasingly agentic workloads, inference patterns are becoming more dynamic, driving a shift towards serverless deployments and on-demand scaling. In this environment, cold-start latency is becoming an increasingly important bottleneck.

As the following graph shows, vLLM v0.9.0 had particularly high cold-start latency, which was substantially reduced (nearly 2x) in the subsequent release (vLLM v0.10.0). We need another such leap in cold-start latency to keep pace with these evolving workloads and the shift towards serverless inference.
